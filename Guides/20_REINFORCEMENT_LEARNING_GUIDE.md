# Reinforcement Learning

Reinforcement learning (RL) addresses the problem of an agent that learns to take actions in an environment to maximize cumulative reward. Unlike supervised learning, training data is not given in advance — it is generated by the agent's own interactions with the environment. This guide covers the formal RL framework (Markov decision processes, value functions, policies), the major algorithm families (tabular methods, deep Q-networks, policy gradients, actor-critic), the standard simulation environments, and the practical pitfalls that make RL training notoriously difficult.

## 1. The RL Framework

The RL setup involves five elements:

| Element | Symbol | Description |
|---------|--------|-------------|
| State | $s$ | The configuration of the environment at a moment in time |
| Action | $a$ | A choice the agent makes |
| Reward | $r$ | A scalar feedback signal from the environment |
| Policy | $\pi$ | A mapping from states to actions (or a distribution over actions) |
| Environment | — | The system that produces next states and rewards in response to actions |

The interaction loop:

```
s_0 -> a_0 -> (r_1, s_1) -> a_1 -> (r_2, s_2) -> ...
```

The agent's objective is to maximize the expected cumulative reward over time, typically discounted by a factor $\gamma \in [0, 1)$ that weights immediate rewards more than distant ones.

### 1.1 RL vs Supervised Learning

| Property | Supervised | Reinforcement |
|----------|------------|---------------|
| Training data | Given upfront | Generated by interaction |
| Feedback | Correct answer per example | Scalar reward; possibly delayed |
| Objective | Minimize prediction error | Maximize cumulative reward |
| Data distribution | Fixed | Depends on the agent's policy (non-stationary) |
| Stability | Generally well-behaved | Notoriously unstable |

These differences make RL practically harder than supervised learning. A correctly-implemented supervised algorithm usually trains; an RL algorithm often does not.

## 2. Markov Decision Processes

A Markov decision process (MDP) is the formal model of an RL problem. It is a tuple $(S, A, P, R, \gamma)$ where:

| Component | Meaning |
|-----------|---------|
| $S$ | Set of states |
| $A$ | Set of actions |
| $P(s' \mid s, a)$ | Transition probability: probability of moving to $s'$ from $s$ after taking $a$ |
| $R(s, a, s')$ | Reward function |
| $\gamma$ | Discount factor |

The defining property — the *Markov property* — is that the next state depends only on the current state and action, not on the history. Real environments often violate this; in practice, the state is engineered to include enough history (or recent observations) to make the Markov assumption approximately hold.

### 2.1 Episodic vs Continuing Tasks

- **Episodic** tasks have a terminal state and natural episode boundaries (a game, a navigation task).
- **Continuing** tasks have no terminal state (process control, dialog systems).

Most RL algorithms are easier to apply to episodic tasks. Continuing tasks usually require an explicit discount factor $\gamma < 1$ to keep returns finite.

## 3. Value Functions and the Bellman Equations

Two value functions are central to RL:

| Function | Definition | Interpretation |
|----------|------------|----------------|
| State value $V^\pi(s)$ | Expected return from $s$ following policy $\pi$ | "How good is this state under this policy?" |
| Action value $Q^\pi(s, a)$ | Expected return after taking $a$ in $s$, then following $\pi$ | "How good is this state-action pair under this policy?" |

The Bellman equations express these recursively:

$$V^\pi(s) = \mathbb{E}_{a \sim \pi}[R(s, a) + \gamma V^\pi(s')]$$

$$Q^\pi(s, a) = R(s, a) + \gamma \mathbb{E}_{s'}[V^\pi(s')]$$

Most RL algorithms can be derived from one of two strategies:

1. **Value-based**: estimate $Q^*$ (the optimal action value); the policy is to act greedily with respect to it. Examples: Q-learning, DQN.
2. **Policy-based**: parametrise the policy directly and optimize its parameters by gradient ascent on expected return. Examples: REINFORCE, policy gradient methods.
3. **Actor-critic**: combine both — a policy (actor) and a value estimator (critic). Examples: A2C, PPO, SAC.

## 4. Tabular Q-Learning

When the state and action spaces are small and discrete, $Q$ values can be stored in a table. Q-learning updates the table using the temporal-difference error:

$$Q(s, a) \leftarrow Q(s, a) + \alpha \left[ r + \gamma \max_{a'} Q(s', a') - Q(s, a) \right]$$

```python
import numpy as np

def q_learning(env, n_episodes=5000, alpha=0.1, gamma=0.99, eps=0.1):
    n_s = env.observation_space.n
    n_a = env.action_space.n
    Q = np.zeros((n_s, n_a))

    for _ in range(n_episodes):
        s, _ = env.reset()
        done = False
        while not done:
            # Epsilon-greedy action
            if np.random.rand() < eps:
                a = env.action_space.sample()
            else:
                a = int(np.argmax(Q[s]))

            s_next, r, terminated, truncated, _ = env.step(a)
            done = terminated or truncated

            # Q-learning update
            Q[s, a] += alpha * (r + gamma * np.max(Q[s_next]) - Q[s, a])
            s = s_next
    return Q
```

### 4.1 Key Hyperparameters

| Parameter | Role | Typical range |
|-----------|------|---------------|
| Learning rate $\alpha$ | Step size of the update | 0.01–0.5 |
| Discount $\gamma$ | Weight on future rewards | 0.9–0.999 |
| Exploration $\epsilon$ | Probability of random action | Often decayed from 1.0 to 0.01 |

Tabular Q-learning has strong convergence guarantees for small finite MDPs but does not scale to large or continuous state spaces.

## 5. Deep Q-Networks (DQN)

DQN replaces the Q-table with a neural network $Q(s, a; \theta)$ that approximates action values. Two innovations make training stable:

| Technique | Purpose |
|-----------|---------|
| Replay buffer | Stores transitions; samples a random mini-batch each update — breaks correlation between consecutive samples |
| Target network | A delayed copy of $Q$ used to compute targets — prevents the optimisation target from chasing the model |

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class QNetwork(nn.Module):
    def __init__(self, obs_dim, n_actions):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(obs_dim, 128), nn.ReLU(),
            nn.Linear(128, 128), nn.ReLU(),
            nn.Linear(128, n_actions),
        )

    def forward(self, x):
        return self.net(x)


def dqn_loss(q_net, target_net, batch, gamma=0.99):
    s, a, r, s_next, done = batch
    q_pred = q_net(s).gather(1, a.unsqueeze(1)).squeeze(1)
    with torch.no_grad():
        q_next = target_net(s_next).max(dim=1).values
        q_target = r + gamma * q_next * (1 - done)
    return F.smooth_l1_loss(q_pred, q_target)
```

### 5.1 DQN Variants

| Variant | Key idea |
|---------|----------|
| Double DQN | Decouple action selection (online net) from action evaluation (target net) — reduces overestimation |
| Dueling DQN | Separate value and advantage streams in the network |
| Prioritised Experience Replay | Sample high-error transitions more often |
| Rainbow DQN | Combines six DQN improvements |

## 6. Policy Gradient Methods (REINFORCE)

Policy gradient methods parametrise the policy $\pi_\theta(a \mid s)$ and update $\theta$ by gradient ascent on expected return.

The REINFORCE algorithm uses the policy gradient theorem:

$$\nabla_\theta J(\theta) = \mathbb{E}_{\pi_\theta} \left[ \sum_t \nabla_\theta \log \pi_\theta(a_t \mid s_t) \cdot G_t \right]$$

where $G_t$ is the return from time $t$ onward.

```python
def reinforce_step(policy, optimizer, log_probs, rewards, gamma=0.99):
    # Compute returns (discounted sum of rewards from each timestep)
    returns = []
    G = 0
    for r in reversed(rewards):
        G = r + gamma * G
        returns.insert(0, G)
    returns = torch.tensor(returns)
    returns = (returns - returns.mean()) / (returns.std() + 1e-8)   # baseline

    loss = -torch.stack([lp * R for lp, R in zip(log_probs, returns)]).sum()
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
```

REINFORCE has high variance because returns vary widely between episodes. Subtracting a baseline (a state value, or just the batch mean) reduces variance without changing the expected gradient.

## 7. Actor-Critic Methods (A2C, PPO)

Actor-critic methods combine a policy network (actor) with a value network (critic). The critic estimates the value function and is used as a baseline in the policy gradient update.

| Algorithm | Idea |
|-----------|------|
| A2C (Advantage Actor-Critic) | Synchronous actor-critic; advantages estimated from value function |
| PPO (Proximal Policy Optimization) | Clipped policy update; stable and widely used |
| SAC (Soft Actor-Critic) | Maximum-entropy off-policy actor-critic; strong on continuous control |
| TD3 (Twin Delayed DDPG) | Continuous control with target smoothing and delayed policy updates |

PPO has become the default policy-based algorithm for many applied RL problems due to its stability and ease of tuning.

### 7.1 Using Stable-Baselines3

For applied work, implementing RL algorithms from scratch is rarely necessary. `stable-baselines3` provides reference implementations of all major algorithms.

```python
# pip install stable-baselines3 gymnasium
import gymnasium as gym
from stable_baselines3 import PPO

env = gym.make("CartPole-v1")

model = PPO("MlpPolicy", env, verbose=0)
model.learn(total_timesteps=50_000)

obs, _ = env.reset()
done = False
while not done:
    action, _ = model.predict(obs, deterministic=True)
    obs, reward, terminated, truncated, _ = env.step(action)
    done = terminated or truncated
```

## 8. Environments and Gymnasium

Gymnasium (the maintained fork of OpenAI Gym) is the standard interface for RL environments.

```python
import gymnasium as gym

env = gym.make("CartPole-v1")
obs, info = env.reset(seed=0)

action = env.action_space.sample()             # random action
obs, reward, terminated, truncated, info = env.step(action)

env.observation_space      # Box, Discrete, Dict, etc.
env.action_space           # same set of types
```

### 8.1 Common Environment Categories

| Category | Examples | Use |
|----------|----------|-----|
| Classic control | CartPole, MountainCar, Acrobot, Pendulum | Algorithm prototyping |
| Box2D | LunarLander, BipedalWalker | Continuous control benchmarks |
| Atari (via ALE) | Breakout, Pong, Space Invaders | Discrete-action benchmarks; image observations |
| MuJoCo | Hopper, HalfCheetah, Humanoid | Continuous-control benchmarks |
| ProcGen | Procedurally generated games | Generalisation benchmarks |

For non-standard problems, custom environments are defined by subclassing `gym.Env` and implementing `reset`, `step`, and `render` (optional).

## 9. Reward Design

The reward function is the most influential design choice in an RL system. Poorly-shaped rewards produce unintended behaviours regardless of algorithm choice.

### 9.1 Reward-Shaping Patterns

| Pattern | Effect |
|---------|--------|
| Sparse rewards (only at goal) | Honest specification but very hard to learn |
| Dense shaping (intermediate rewards) | Faster learning; risk of teaching shortcuts |
| Negative time-step penalty | Encourages efficiency |
| Action-cost penalty | Encourages economy of action |
| Curriculum (gradual difficulty) | Bootstraps learning on complex tasks |

### 9.2 Reward Hacking

Agents optimise the specified reward exactly — including ways the designer did not anticipate:

| Specification | Exploit |
|---------------|---------|
| "Reach the goal" | Agent finds a glitch in the simulator |
| "Maximize forward speed" | Robot somersaults along the floor |
| "Collect coins" | Agent learns to glitch through walls to collect duplicate coins |

Reward design is iterative. Observing agent behaviour and adjusting the reward function is part of the workflow, not a setup step.

### 9.3 Sparse-Reward Strategies

| Approach | Idea |
|----------|------|
| Reward shaping | Add intermediate signals; risk of teaching shortcuts |
| Curiosity-driven exploration | Add intrinsic reward for novel states |
| Hindsight Experience Replay (HER) | Replay failed episodes with the achieved goal as the target |
| Imitation learning | Bootstrap from demonstrations |

## 10. Common Pitfalls

| Pitfall | Symptom | Mitigation |
|---------|---------|------------|
| High variance across seeds | Some seeds learn, others do not | Run multiple seeds (5–10) and report variance |
| Reward not shaped well | Agent fails to learn or learns the wrong thing | Inspect reward distribution; add intermediate signals |
| Hyperparameters not tuned to environment | Algorithm fails on a simple task | Try published hyperparameters for similar environments first |
| Environment non-stationary | Performance degrades after initial gains | Add target network; tune learning rate |
| Insufficient exploration | Agent stuck in local policy | Increase $\epsilon$ or entropy bonus; try a different initialization |
| Insufficient training time | Returns still rising at end of training | RL needs orders of magnitude more samples than supervised; budget accordingly |
| Off-by-one errors in episode boundaries | Subtle but pervasive bugs | Use a tested implementation (stable-baselines3) for production work |
| Discount factor too low | Agent ignores long-term consequences | Increase $\gamma$ toward 0.99 or higher |

RL is empirical: published claims have been shown to be highly sensitive to seed, implementation details, and codebase choices. A new RL algorithm requires extensive multi-seed evaluation before claims of superiority over baselines are trustworthy.
